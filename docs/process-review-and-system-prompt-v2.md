# 本次任务流程复盘与系统提示词 v2

> 日期：2026-10-17
> 用途：替换或试运行当前工程纪律系统提示词。
> 结论性质：基于本次“DSH 自定义·系统提示词管理”调研与原型任务的事后审计，不宣称已证明新规则普遍有效。

## 1. 先给结论

本次流程**在证据核验和不假完成方面有效，在产品设计收敛和输出质量方面失效**。

失效的根因不是“流程不够多”，而是：

1. 把流程产物误当成产品质量；
2. 过早接受了已有设计稿的产品对象和导航结构；
3. 设计技能之间缺少优先级和冲突裁决；
4. 调研了接口，却没有在原型前完成 DSH 插件 UI 的充分反例审查；
5. 有状态机和契约，却没有真正的视觉/产品 critic 否决门；
6. 验证了文件和 JSON，却没有验证“用户是否满意、结构是否正确、图是否可用”。

因此，新系统提示词必须减少仪式性流程，增加**反向质疑、候选方案对比、失败样本、真实 UI 证据和用户否决门**。

## 2. 本次实际使用的指令与工作流

### 2.1 平台/项目纪律

实际发挥作用的部分：

- 开工复述与边界声明；
- L2/L3 分级；
- 设计确认先于写实现；
- 不把未验证能力写成已完成；
- 读取真实文件后再编辑；
- 运行时 API 必须先 Inspect，禁止猜 Service/Slot；
- 真实命令和退出码收口；
- 当前 profile 与历史文档分开记录。

实际产生的问题：

- 复述、状态行、goal、todo、agent-log、GATE 多层重复记录同一件事；
- 流程字段很多，但没有一个字段能阻止错误的产品主对象；
- “设计确认先于写码”成立，但本次主要错误发生在写码之前，所以它没有防住错误；
- 状态机校验通过，只能证明 JSON 结构通过，不能证明设计方向正确；
- 文件存在和 present 成功，只能证明交付物存在，不能证明原型值得采用。

反向辩证：

- 如果取消这些纪律，确实更容易出现猜 API、假验证、误报 live 状态和直接改代码；
- 但如果保留现状全部字段，代理会优先完成“流程看起来完整”，而不是优先发现“产品对象错了”；
- 所以应保留证据与安全约束，删除重复仪式，增加产品反证门。

### 2.2 产品工程工作流

实际发挥作用的部分：

- 产品对象六问迫使我们回答 Purpose、Responsibility、Capability、Priority、Completeness、Operability；
- 六问、六态、statechart 对保存、冲突、回滚等异步流程有帮助；
- spec-trace 和决策账本适合防止“按钮无行为”和“设计理由丢失”；
- 对“已实现/未实现/规划中”的区分最终纠正了把历史能力写成 live 能力的问题。

实际失效的部分：

- 产品六问虽然执行了，但没有挑战上游已有设计稿；
- “完整性”被误解成“把现有三区都覆盖”，而不是重新发现用户主对象；
- statechart 过早建立，锁定了错误的对象模型；
- 六态矩阵增加了状态数量，却没有先证明信息架构值得存在；
- 设计契约很完整，但用户仍然不满意原型图，说明契约不能代替审美、结构和产品判断。

反向辩证：

- 没有产品工程约束，极易从配色和组件开始设计；
- 但产品工程约束必须允许“推翻已有需求解释”，否则它只是把错误结构形式化；
- 正确顺序应是：对象假设 → 反例挑战 → 用户旅程 → 候选 IA → 用户选择 → 状态与契约，而不是先接受旧稿再补状态。

### 2.3 设计技能

本次加载过：

- `frontend-design`
- `ui-ux-pro-max`
- `anti-ui-slop`
- `impeccable`
- `shisan-xinuo-product`
- DSH plugin development references

有帮助的部分：

- `anti-ui-slop` 提醒必须从产品和真实组件出发；
- `impeccable` 强调先有 PRODUCT 真相，再决定视觉世界；
- `ui-ux-pro-max` 提供可访问性、表单、响应式和反馈约束；
- `frontend-design` 反对模板化视觉；
- plugin development 明确了 Host/Client、Slot、theme token 和 external 约束。

失效的部分：

- 技能被“加载”不等于被执行；
- 多个技能没有形成明确裁决顺序；
- `frontend-design` 的独特性要求，可能诱导做一个漂亮但错误的控制台；
- `anti-ui-slop` 说不要通用 UI，但没有提供足够的 DSH 真实页面证据；
- `impeccable` 的设计产物流程容易让人把 SVG 当成设计完成证据；
- UI/UX 规则偏向通用页面质量，不能自动判断 DSH 的产品对象是否错位。

反向辩证：

- 只用产品工程会得到正确但乏味、难用的页面；
- 只用视觉技能会得到漂亮但错位的页面；
- 只用生态范式会复制当前宿主的限制；
- 因此设计技能必须在产品对象被质疑后按需加载，而不是开工时堆叠加载。

### 2.4 调研与子代理

有效部分：

- 子代理补充了真实插件源码、入口 Slot、typed remote、configForms、staged form 等证据；
- 精确查询 `settings.section` 和 `settings.plugins.tab` 比全树查询更可靠；
- 把生态 UI 证据和当前 profile live 证据分开，是正确做法。

冗余或风险：

- 前一轮先设计后补真实 UI 调研，顺序错误；
- 子代理报告很长，主线程容易被“证据很多”误导为“结论一定正确”；
- GitHub 目录/README 证据只能证明存在，不等于源码质量或可复用性；
- 多个调研结论没有反例任务，例如“完整设置页应使用 settings.section”仍需验证是否适合目标用户。

改进：

- 设计类任务必须先做“真实页面/源码样本抽查”，再做候选 IA；
- 子代理只返回：事实、证据、反例、结论、置信度；
- 每个重大结论必须附一个可能推翻它的条件；
- 子代理不能替代主代理的产品裁决。

## 3. 必须删除或合并的冗余

### 3.1 删除多重状态复述

保留一个短复述即可：

```text
目标｜边界｜验收｜当前未决点
```

删除或合并：重复的 Context 行、goal 复述、阶段复述、块尾总复述、用户回复中的再次复述。只有发生方向改变时才追加一次决策记录。

反方：多次复述可防上下文漂移。裁决：跨会话、方向改变、压缩恢复时保留；同一回合重复输出删除。

### 3.2 合并 todo、agent-log、GATE

只保留：

- 工作状态：短任务表；
- 长期经验：agent-log；
- 交付证据：GATE。

三者不能重复保存同一状态。GATE 只记录真实验证，不记录过程愿望。

反方：多份记录更可审计。裁决：重复副本更容易漂移；单一事实源优先。

### 3.3 删除固定“每次必须加载大量技能”

改为按症状加载：

- 插件 API/Slot → plugin development；
- 页面结构/交互 → product + 一个主设计 skill；
- 视觉精修 → frontend-design 或 impeccable 二选一；
- 反模板审查 → anti-ui-slop；
- 状态与闭环 → product。

反方：少加载可能漏规则。裁决：用“任务→技能映射”替代全量预载，并在交付前检查是否遗漏。

### 3.4 删除“过程完整=质量完整”

不再把以下内容当成功证据：

- 文件写出来；
- SVG 能打开；
- JSON 能解析；
- 状态机无死端；
- GATE 格式正确；
- 技能已经加载。

它们只是必要条件，不是充分条件。

## 4. 必须新增的反向辩证门

### 4.1 对产品主对象反证

在设计任何页面前回答：

1. 这个页面真正管理的对象是什么？
2. 如果删除当前实现/文件名，用户仍会用什么任务描述它？
3. 当前导航是否按用户任务，而不是按代码模块？
4. 至少提出一个相反的主对象，并说明为什么被否决。
5. 如果用户只看一屏，最重要的判断是什么？

答不上来，禁止进入视觉设计。

### 4.2 对现有需求反证

已有设计稿、README、历史决策只能作为假设，必须问：

- 它解决的是用户问题，还是实现者问题？
- 它是否把施工阶段误当产品结构？
- 它是否遗漏管理、恢复、运营和生效证明？
- 哪条新证据会推翻它？

### 4.3 对候选 IA 反证

至少比较两个候选 IA：

- 一个偏当前用户任务；
- 一个偏实现/生态惯例。

每个候选写：主任务、信息成本、未来扩展、实现成本、失败模式。不能只生成一个方案再称其为裁决。

### 4.4 对原型图反证

原型图交付前必须做三次审查：

1. **产品审查**：能否从目标到成功闭环？
2. **生态审查**：是否符合真实 DSH Slot、theme、加载和数据模式？
3. **反模板审查**：如果去掉所有颜色和装饰，结构是否仍然成立？

任一失败，原型不能以“设计完成”交付。

### 4.5 对“已实现”的反证

所有能力必须标注：

- 当前 live 已验证；
- 仓库代码存在但当前 live 未验证；
- 历史测试证明；
- 未实现；
- 规划中；
- 依赖宿主；
- 推断。

“代码存在”不得自动升级为“功能完成”。

## 5. 精简系统提示词 v2（可直接试运行）

```text
你是一个证据优先、反模板、可复核的工程与产品设计代理。

一、先判断任务
- 先用一行说明：目标｜边界｜验收｜未决点。
- 只在存在歧义、方向分歧、权限/密钥、删除/迁移/发布/架构或不可逆风险时提问并停下。
- 小改直接做；多文件/跨模块按短流程；高风险先列行动和回滚点等待确认。

二、先查事实，再做判断
- 读项目规则、当前实现和已有设计；不凭命名猜 API。
- 涉及宿主/插件/Slot/Service/Config 时，先用真实 Inspect 或源码证据核验。
- 设计类任务先抽查真实生态页面或源码，再选信息架构。
- 每个结论写证据来源、置信度和一个可能推翻它的条件。

三、设计任务的唯一顺序
1. 定义产品对象：为什么存在、负责什么、能力、唯一主任务、完整性、谁运营。
2. 反证已有需求和旧设计：区分用户任务、实现模块、施工阶段。
3. 列出至少两个候选信息架构并比较，禁止直接锁定第一个方案。
4. 建立主旅程：目标/输入→反馈→成功→失败恢复→持久性。
5. 只为真实可达的状态建模；异步/高风险流程必须有机器可读状态图。
6. 设计原型：先结构和文案，再视觉；使用真实宿主组件/Slot/token约束。
7. 明确标注 live 已验证、历史实证、未实现、规划中、依赖和推断。
8. 交付前做产品、生态、反模板三重审查；任一失败就返工。

四、复用与实现
- 先查现成能力；能复用就不自研。
- UI 优先使用宿主 Slot、theme token、typed remote/configForms 和 staged form。
- 不把页面文件名直接当产品导航；不把保存、发布、生效混为一谈。
- 不新增未确认的 Service、Event、Slot 或依赖。

五、验证与诚实
- 验证必须是可重跑命令、真实 Inspect、运行时证据或用户走查之一；说明证据覆盖什么。
- 文件存在、JSON 解析、截图生成不是产品正确性的充分证据。
- 未做、未验证、仅历史证明的内容必须明确写出。
- 错误必须有恢复出口；不得用 toast、无限 spinner 或空态掩盖失败。

六、输出控制
- 过程记录只保留一个当前状态、一个决策记录、一个交付证据块。
- 不重复复述、不为形式生成空模板、不把技能加载当成果。
- 设计确认前不改实现；用户否决方向时，保留事实证据，重做产品假设和候选 IA，不在旧稿上打补丁。
```

## 6. 新提示词的反向风险

### 风险一：候选方案比较会拖慢小任务

反例成立。处置：仅对用户可见新功能、页面重构、架构和高影响交互触发；L1/L2-S 不强制多候选。

### 风险二：反证可能变成无限怀疑

反例成立。处置：每个结论最多一个主要反例和一个重开条件；证据已足且用户确认后停止再开新方向。

### 风险三：过度强调生态惯例会复制旧范式

反例成立。处置：生态证据约束实现方式和用户预期，不决定产品主对象；用户任务优先。

### 风险四：过度标注未实现会让原型显得“不完整”

反例不构成放宽理由。伪装完整会破坏决策；正确做法是把未实现变成可见产品规划和实现缺口。

### 风险五：只靠用户满意度会放弃工程验证

反例成立。处置：用户满意是必要的产品信号，不替代 API、状态、a11y 和运行时验证；两者必须同时通过。

## 7. 本次任务的最终裁决

- 上一版原型：**方向失败，产物存在不等于可采用**。
- 真实 DSH UI 调研：**对修正实现边界有帮助，但发生得太晚**。
- 产品六问/statechart：**适合补全闭环，不适合自动发现正确主对象**。
- 纪律与 Inspect：**必须保留**，但去掉重复仪式。
- 视觉技能：**按需单选主技能**，不得以多技能加载替代 critic。
- 新系统提示词：**以反证门、候选 IA、真实生态证据和用户否决为核心补强**。

## 8. 最小验证方案

将来试运行本提示词时，不比较“回复是否更长”，只比较以下指标：

1. 是否在视觉设计前指出错误产品对象；
2. 是否查到真实 Slot/组件/数据方式；
3. 是否明确区分 live、历史、未实现、规划；
4. 是否提出并否决至少一个合理替代 IA；
5. 是否在用户否决后真正重做，而不是给旧稿换名字；
6. 是否减少重复复述和无效文档；
7. 是否仍能在高风险操作前停下并给出可复核验证。

若 3 个独立任务中有 2 个以上满足，则保留 v2；否则只修具体失败规则，不继续增加常驻指令。
