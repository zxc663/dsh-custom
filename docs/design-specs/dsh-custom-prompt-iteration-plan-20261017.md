## 1. 目标与本质（一句话）

**我们要做的插件本质**：把「元工作流纪律」落成 DSH 宿主上可验证的治理体系——**元提示词层**（常驻核心＋用户自定义段，全部允许安装用户修改）＋**工作流与固定模板层**（渐进加载）＋**运行时强制层**（真值收口/边界拦截/强制补判级/审计）。页面「DSH自定义」是这套体系的**配置与证据面**：让维护者看清「模型实际看到什么」、可回滚地修改「该看到什么」、并审计「实际怎么被执行的」。核心承诺三条：**过程可审计、边界可拦截、完成可证明**；不承诺模型更聪明。

### 3.1 提示词配置面（本轮重点规划）

- **常驻核心**：`content/discipline.md`（v8）。**允许用户修改**——页面编辑器直接改；改坏/清空时运行时 fail-closed 回退内置默认（现有装载逻辑 src L1459/L251-260 已具备回退语义，回退会落账）。「恢复出厂默认」一键操作。
- **用户自定义提示词段**（新增，与常驻核心区分开）：存储 `user-prompt.md`，注册为独立 section（建议 order 在常驻核心之后、官方提示词之前，命名 `shisanxinuo:user-prompt`）；页面单独编辑区＋开关＋预览；**空=不注入**；语义定位=安装用户自己的附加纪律/偏好，不覆盖常驻核心。
- **渐进加载层**：`content/layered/` 各分节**同样允许用户修改**（每分节单独编辑/启用/恢复出厂）；强制级 M/S 标注可视化。出厂默认=随包内容，用户改动记录到 audit。
- 护栏沿用已拍板语义 b：允许模型改动存储但必须提示/确认并留痕（防静默改写）；页面保存前快照＋校验（未知变量阻止保存）。

### 3.2 提示词三段的装配序（模型可见顺序）

```
官方系统提示词（宿主）
  ↑ 接管官方 complete 段（可选，独占；与提示词中心互斥提示）
  ↑ 用户自定义段 user-prompt.md（可开关，空=不注入）
  ↑ 常驻核心 discipline.md（可编辑，fail-closed 回退内置）
```

顺序说明：常驻核心在最前（纪律优先）；用户自定义段次之（用户附加约束）；接管 official 的 complete 段与上述互斥（启用 complete 时提示词中心的两段被覆盖——页面需显式冲突提示与出口）。

## 4. 渐进加载怎么保证（保证机制四件＋诚实边界）

**目标**：M 级分节（触发即必须）不能靠模型自觉，S 级分节（按症状）不能被误当常驻。

**保证机制四件（设计，运行时未实现）**：

| 件 | 机制 | 兜底 |
|---|---|---|
| ① 路由契约 | 常驻核心 §8＋00-加载清单：M/S/X 强制级表，模型按触发读分节 | 模型自觉（当前唯一通道） |
| ② 检测→注入 | 宿主检测三信号：判级缺失（D1）/任务清单缺失（D2）/压缩信号（D8）→ 注入对应分节提示 | 一次性注入＋steer 熔断（每回合 1/每任务 3）防死循环 |
| ③ 缺载后果绑定 | M 级分节缺失的后果绑定到收口：对接真相清单没填→断言/收口打回（gate 现有通道）；方案未三想一合→规划模板验收对照缺失→收口不闭环 | 收口侧打回（已实现 R11/R13） |
| ④ 指纹与漂移核对 | 分节装载 fail-closed（loadTextWithFallback 同款）＋段指纹核对（sectionFingerprint 同款，漂移落账） | 用户改坏分节→回退出厂默认＋audit |

**诚实边界（写进文档）**：检测→注入只能保证「触发时注入」，**不能保证模型读了并遵守**——遵守由③收口侧打回兜底；判定「读了」没有可机器证据时，以收口结果为准。

## 5. 收尾输出格式（已入常驻核心 v8 §5，此处为规格说明）

固定骨架（无内容的分节省略，不写「无」充数）：

```
【交付】一句话结果（做了什么、是否达标）
【验证】证据：真实命令＋真实退出码 / 断言结果 / 文件:行号；无机器判据则如实写「未验证」
【改动】变更文件清单（无改动省略）
【待决策】需要用户拍板的问题——每条带分歧点＋推荐选项＋替代后果（对齐提问形态）
【待授权】approval 待批事项——列出拟执行动作与原因，等用户批准，未批准不得执行
【未决/风险】未验证项与风险（真待办）
```

- **告知用户的**：交付/验证/改动/待决策/待授权/未决——一切影响用户判断与后续动作的信息；
- **不告知的**：内部流程步骤（需求四层分析/三质疑过程/候选方案罗列）——落承载与流水，不占输出面，除非用户要求；
- **待决策 vs 待授权**：待决策=意图/方案类选择（用户拍板方向）；待授权=approval 类（用户批准动作）——两者分节列出，不混写。

## 8. 文档更新流程（必要流程）

**触发**：任何代码/提示词/配置/接口/规则变更、任何拍板决策、任何验证结论变化。

1. **同批更新**：变更与文档更新同一批完成，不「先改代码、文档以后补」——只改实现不更新文档=半成品交付。
2. **更新清单（按变更类型）**：
   - 提示词变更 → `content/discipline.md`＋镜像 `agents-md-discipline.md`＋设计文档对应节＋版本号递增；
   - 实现变更 → README 能力矩阵与状态总表＋CHANGELOG＋对应设计/证据文档；
   - 规则/流程变更 → 设计文档辩证表＋layered 对应分节＋00-加载清单。
3. **检查**：grep 旧版本号/旧条款无残留；交叉引用节号一致；「已实现/设计要求」标注与真实状态一致（防把规划写成品、把部分写全部）。
4. **留痕**：变更与文档更新同批进承载流水（精确到分）与 git 提交。
5. **季度对账**（人侧触发）：文档与实现逐项对账，漂移纠偏留档。

**反向辩证**：收益=文档与实现不漂移，下个会话与用户不读旧档；反例=一行小改也走全量流程=仪式税；副作用=文档维护成本上升；缓解=一行改动只更新对应小节＋版本行，不全量重写；「部分实现 vs 规划」状态标注随变更同步。
